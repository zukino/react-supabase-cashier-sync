# App Flow Document for React Supabase Cashier Sync

## Onboarding and Sign-In/Sign-Up

When a new user first arrives, they land on a clean, branded welcome page that briefly describes the cashier application and offers two primary actions: Sign In or Sign Up. If the user chooses to sign up, they are taken to a registration form that prompts for an email address and password. The form enforces strong password rules via Zod validation, ensuring the password meets complexity requirements before submission. Alternatively, if the project is configured for social or third-party logins, the user may also click a provider button (for example, Google or GitHub) which directs them through that provider’s OAuth flow before returning them to the app with a valid session token. Once the registration form is submitted, Supabase handles user creation on the backend and issues an authentication token. Upon successful account creation, the user is automatically signed in and redirected to the main dashboard. 

If an existing user clicks Sign In, they enter their credentials in a login form that again validates inputs using Zod. On submission, Supabase authenticates the credentials and returns a session. If credentials are invalid, a clear error message appears above the password field. A “Forgot Password” link beneath the form leads the user to a password recovery page where they enter their email. Supabase sends a reset link to that address. Clicking the link in the email opens a secure reset form where the user chooses a new password, which is then saved via the Supabase API. After a successful reset, the user is taken back to the sign-in page. Throughout the session, the user can sign out at any time by clicking the Sign Out button in the header, which calls Supabase’s sign-out endpoint and returns the user to the welcome page.

## Main Dashboard or Home Page

After a successful sign-in, the user lands on the Main Dashboard, which features a top header bar showing the application name, a sync status indicator, a theme toggle button for light and dark modes, and a user menu with the Sign Out option. Beneath the header, a horizontal menu or sidebar navigation presents labels for Sales, Inventory, Customers, Reports, and Settings. Each of these sections is visually represented with accessible icons provided by Radix UI, styled via Tailwind CSS. In the central area of the dashboard, the default view is the POS sales screen, which shows a list of products or a search field, the active transaction list on the right, and a numeric keypad area below for quick entry. This layout is built from shadcn/ui components, making it fully responsive and keyboard-navigable. From this dashboard, the user can click on any navigation label to transition into the corresponding module.

## Detailed Feature Flows and Page Transitions

On the Sales page, the user begins a new transaction by typing a product name or scanning a barcode. As each item is added, a row appears in the transaction list showing quantity, price, and a delete icon. The user may click on a row to adjust the quantity or apply a discount. Once all items are entered, the user clicks the Pay button, which opens a modal dialog. This dialog prompts for payment type, amount tendered, and any change to return. The form is built with React Hook Form and validated with Zod to ensure numbers are correct. Submitting the payment saves the order to the local SQLite database and triggers a TanStack Query mutation to schedule a background sync. A confirmation message appears and a printable receipt is rendered.

Switching to the Inventory page, the user sees a table of existing products with columns for name, SKU, stock level, and price. A search input above the table filters products in real time. Clicking Add Product navigates to a form page where the user enters item details using accessible form fields. Each input is validated and on save, the new record is written immediately to the local database through the local-db service and queued for Supabase synchronization. Editing a product follows the same flow but pre-populates the form.

In the Customers section, the user can view a list of customers or click Add Customer to open a slide-in panel. The panel contains fields for name, contact information, and notes. Saving writes data locally and flags it for sync. From any list page, the user may click a row to view details, edit fields, or delete the record. Each operation uses React Hook Form for validation and TanStack Query for local mutations and background sync triggers.

The Reports page provides charts and tables summarizing sales by day, week, or month. The user selects a date range from a date picker, and the page fetches aggregated data from the local database. Framer Motion is used for smooth transitions between chart states. The user can export a CSV of the displayed report, which is generated on the client side.

All of these feature pages include a persistent Sync Status component in the header that shows states like “Offline,” “Syncing...,” or “Last synced 3 minutes ago.” If desired, the user can click a manual Sync Now button that invokes the sync service immediately.

## Settings and Account Management

Under the Settings section, the user finds a Profile page where they can update their email address and change their password. The email update flow requires re-authentication via a password prompt. The password change flow demands the user’s current password and the new password, with confirmation and validation. Below profile settings, a Preferences sub-page allows the user to configure theme defaults, notification preferences for sync successes or failures, and local data retention options. Each change is saved locally and, if relevant, mirrored to Supabase metadata. From any settings page, a Back link or breadcrumb leads the user back to the Main Dashboard.

## Error States and Alternate Paths

Whenever the user submits invalid data—such as leaving a required form field blank or entering a non-numeric value where a number is expected—the form highlights the offending field in red and displays a clear, human-readable error message. If a network request fails during login, sync, or data fetch, the application displays an error toast at the top right corner indicating the issue and suggesting an action, such as checking internet connectivity. In the event of offline operation, the Sync Status component shows an offline indicator. All write operations continue to work locally, and the user sees a warning banner explaining that changes will sync once connectivity is restored. If the synchronization engine encounters a conflict—such as simultaneous edits on two terminals—the user is shown a conflict resolution screen where they can compare versions, choose which data to keep, or merge fields manually. A global error boundary ensures that any unhandled exception is caught and a friendly fallback UI appears, offering a reload button.

## Conclusion and Overall App Journey

In a typical journey, the user discovers the cashier application, registers or signs in, and lands on the dynamic POS dashboard. They quickly add products and complete a sale, relying on instant local commits to the SQLite database. Throughout the day, they manage inventory, add new customers, and view sales reports. All these actions are captured locally and seamlessly synchronized with the Supabase backend every five minutes or on demand. Should connectivity falter, the user remains productive offline, confident that data integrity is maintained and conflicts are surfaced clearly. At any time, they can update their account details or preferences in Settings, sign out securely, and return later to resume work. This flow ensures a modern, reliable, and responsive cashier experience from sign-up to everyday operation.
